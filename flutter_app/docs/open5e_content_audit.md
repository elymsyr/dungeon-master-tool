### Scope — everything, from scratch

**In scope:** the 19 bundled Open5e packs in `assets/open5e_packs/` and the offline
importer that produces them — **all of it, including content that already ships and
fields that already measure 100%.** This is a from-scratch pass, not a gap-filling

- A ✅ row is a **claim to re-verify**, not a result to trust. `audit_packs.dart`
  counts values, not correctness; the ⚠ marker exists because several categories

- Every card that already ships is re-examined for the question §2 asks: *should
  this entity exist at all, or is it a copy of something already in scope?*
- Every ⛔/⚪ policy row is re-derived rather than inherited. Several of them
  ("no base items ship in item packs", "a class `_ref` would dangle") were written

### The target architecture — read before writing a mapper fix

Every fix in §6 obeys two contracts. The first (§2) is new and takes precedence
when they interact: **never create what you can link.** The second is the
**named-field grant system** that replaced the effect DSL on 2026-07-28.
`vault/20-Systems/Grant-Resolution.md` is the authority on it;
`CharacterResolver.grantFieldKeys` is the closed 41-key contract. Four rules
constrain what a correct fix looks like:

1. **One mechanic, one field.** There is no `kind`/`predicate`/`scales_with` row
   language any more — `FieldType.featEffectList` and `grantedModifiers` are
   deleted. Never invent a key; if a mechanic has no field, that is a schema
   change with four guards to satisfy (`grant_contract_test`,
   `grant_field_isolation_test`), not an importer change.
2. **Class, Subclass and Background deliberately do NOT carry the grant block.**
   Seeing `subclass` at 1-of-8 filled and "fixing" it by handing it the block
   would recreate exactly the two-fields-one-mechanic ambiguity the removal was
   for — and `grant_contract_test` fails on it. Their grants go in their own
   typed fields (`saving_throw_refs`, `armor_training_refs`, `granted_skill_refs`,
   …), and everything level-gated goes on a `features` row.
3. **Level-gated mechanics live on a Feat card, referenced from the `features`
   row** — `{level, name, description, granted_feat_refs, granted_trait_refs, …}`.
   The class card names *which* feat arrives at *which* level; the Feat card
   carries the mechanics via the grant block. This is the forward edge that
   replaced `feat.auto_granted_by`. Scaling is a `{lvl: value}` table
   (`extra_attack_count_by_level`), never a formula.
4. **Nothing is silently dropped.** Rules the engine cannot pre-compute
   (advantage, rerolls, roll-time riders, timing) belong in `mechanical_notes`,
   one rule per line — they render on the sheet under "Other Effects". Today
   `mechanical_notes` is **0% across every bundled category**, which means every
   §5 row below reading "stays in prose" is currently invisible to the player.
   Routing them there is the cheapest real win in this audit (§6 B5).

## 1. Why this exists

Five distinct gaps, with five distinct fixes. Do not conflate them. Gaps 1–3 are
about the **assets**; gaps 4–5 are about everything between a correct asset and a
player seeing it, and were added by the 2026-07-30 gap analysis.

**Gap 1 — empty fields.** The bundled packs ship the right **entities** but mostly
empty **fields**. A player installing *Tome of Heroes* gets 76 subclasses that
attach to the correct parent class and then grant nothing — they carry
`description` and `parent_class_ref` and not one other field. → §5, phases B1–B7.

**Gap 2 — duplicated entities.** 20.9% of the bundled corpus shares a
`(slug, name)` key with content already in scope: 1,660 keys the built-in SRD pack
ships, and 3,393 copies of names appearing in more than one bundled pack. Since
2026-07-29 a package can **link** another instead of copying it, so the genuine
duplicates are deletions, not merges. **But most of that 20.9% is not duplication
at all**, and L0 has now measured how much: **3,153 of the 4,331 redundant copies
are rows owned by a single statblock**, and of the 2,540 cross-pack shared names
only 188 carry identical prose while 1,749 say different things (§3.2). The
actionable set is **1,178 entities (5.7%)**, dominated by `monster` reprints and
the gear stubs. Read 20.9% as a collision surface; the policy table drives the
work. → §2, §3.2, phases ~~L0~~–L2.

**Gap 3 — refs written as prose.** Where a card *should* point at another card, the
importer mostly writes English instead. `feat.prereq_class_refs` is 0% because the
prerequisite class is named in the description text; `spell.class_refs` is 0%
because of a policy note that package links have now invalidated. Only **135**
cross-package refs exist in the entire 20,712-entity corpus. → §2.3, and a gate on
every B phase.

**Gap 4 — readers that cannot see a correct ref.** The sheet resolves every
envelope shape; **the wizard does not**. Four chargen call sites read
`spell.class_refs` as a raw `List<String>` of ids and match with `.contains()`, so
the softRef Map that §2.3 tells you to write matches *nothing* there — and today's
packaged spells are visible only through a `tags` fallback that the same fix would
retire. Filling a field is therefore not the last step; §2.3.1 and Stage U are. →
outcome 4.

**Gap 5 — nothing published.** `emit.dart` hardcodes `pack_version: '1.0.0'`,
`build_catalog` derives the immutable `r2_path` from that version, and
`publish_catalog` **skips** an object that already exists unless `--force`. Every
pack is `1.0.0` and already uploaded, so a perfect rebuild changes nothing for any
user, and no installed pack has an upgrade trigger. → Stage D.

The wiring for what does exist is not the problem. All 97 `parent_class_ref`
softRefs on the bundled subclasses resolve by name against the built-in SRD classes
(Cleric ×11, Wizard ×11, Monk ×9, …, zero misses). That is the model the rest of
this work copies.

## 2. The linking contract — never create what you can link

**This is the most important rule in this document, and it outranks every fill
target in §5.** A row that reaches 100% by minting duplicate cards is a
regression, not a fix.

Package links landed on 2026-07-29 (`vault/20-Systems/Package-Links.md`). A package
can now **link** another package: the two stores stay separate, nothing is copied,
and the linked package's entities become visible inside the linking package and
follow it into every world import, catalog download and character build. That
mechanism is finished and tested. This audit is the content work it unblocked.

### 2.1 The built-in pack is already in scope everywhere — do not re-ship it

Every bundled pack effectively links the built-in SRD 5.2.1 pack already, through
three independent paths, none of which needs a declaration:

| Context | Why built-in content is in scope |
|---|---|
| Package editor | `packageReferenceOverlayProvider(name)` = built-in SRD entities ∪ the closure's entities, injected read-only by `EntityNotifier(referenceOverlayFor:)` |
| World | `SrdCoreBootstrap.ensureImported` links `SRD 5.2.1 Core` into every D&D-5e-v2 world at creation, and self-heals a world missing the link |
| Character creation / resolve | `mergeBuiltinWithPackages` starts from the built-in map and layers packages on top; `layerCharacterPackages` does the same on the card side |

**Consequence:** a bundled pack that ships its own "Acolyte" — the *same* Acolyte —
is not adding content. It is shadowing content that is already there, and it costs
the user a duplicate row in every picker. Those entities should simply not be
emitted.

**The consequence is about identical content, not identical names.** §2.5 measures
how often those two come apart: a pack's "Fireball" may be an A5E restat, and its
"Amphibious" is usually a per-creature sentence that only *looks* like the built-in
row. Establish which one you are holding before deleting anything.

An explicit `metadata.links` entry pointing at the built-in pack is therefore
**unnecessary** — and would be wrong in the catalog, which has no entry for a
built-in pack.

### 2.2 Pack→pack links need a declaration — and it needs both keys

For the 3,393 copies shared *between* bundled packs, one pack keeps the content and
the others link it. That link is declared in the pack payload:

```jsonc
// in a *.pkg.json, alongside title / license / pack_version
"metadata": {
  "links": [ { "slug": "open5e-toh", "name": "Tome of Heroes" } ]
}
```

**Both keys are required, and they hold different strings.** This is the sharp edge
of the whole phase:

- `slug` — the **catalog slug**, i.e. the target's `package_name`
  (`open5e-toh`). `build_catalog._requiredSlugs` reads `slug ?? package_id ?? name`
  and emits it as the catalog entry's `requires`, which `FirstPartyInstallNotifier`
  resolves transitively before installing. A link carrying only `name` produces a
  `requires` entry matching no manifest slug — silently skipped at install.
- `name` — the **installed local package name**, which is the target's
  `metadata.title` (`Tome of Heroes`), because `PackagePayloadImporter` names the
  local row after the title and falls back to the slug only when there is none.
  `PackageLink.fromJson` reads `package_id`/`packageId` and `name`/`package_name`
  and **ignores `slug` entirely**, so a link carrying only `slug` resolves to
  nothing in the app.

All 19 titles are currently unique, so name resolution is unambiguous.
`PackageLinkService` resolves `package_id` first and falls back to `name`; leave
`package_id` out of a built payload, since the local row id is minted at install.

Today **every pack emits `requires: []`** — the wiring exists end to end and has no
data flowing through it.

### 2.3 Links inside cards — the part that is easy to get wrong

Dropping duplicate *entities* is only half of it. The other half is that **every
reference a card makes must resolve to existing content, not create a new copy of
it and not sit in prose.** This applies to every field in §5 that ends in `_ref`
or `_refs`, and it is the main way a B phase can quietly make things worse.

The worked example: an official pack's feat has "Prerequisite: Paladin" in its
description. There are three ways to "fix" `prereq_class_refs`, and two are wrong.

| | What it does | Verdict |
|---|---|---|
| Mint a `class` card named "Paladin" in the pack and hard-`ref` it | adds a 3rd Paladin to the user's picker; the character's actual Paladin levels are on the *built-in* Paladin, so the gate silently never matches | ❌ never |
| Leave it in the description | prerequisite is invisible to the wizard's gating; the field stays 0% | ❌ that is the current state |
| `softRef('class', 'Paladin')` | `resolveEntityRef` → `findEntityIdByName` lands on whichever Paladin is in scope — the built-in one — at resolve time | ✅ |

Resolution order for **any** ref the importer emits:

1. Tier-0 vocabulary (ability, skill, damage type, condition, size, sense, …) →
   `lookup()` → `{_lookup, name}`, resolved to the campaign's Tier-0 uuid at import.
   Unchanged by any of this.
2. Target exists in the **built-in pack** → `softRef(slug, name)`, and **do not
   emit a local copy of that entity**.
3. Target exists in **another bundled pack** → `softRef(slug, name)` **and** add
   that pack to `metadata.links` (§2.2). A softRef alone still resolves in a world
   where both packs happen to be installed, but the link is what makes that
   happen on purpose.
4. Target ships in **this pack and nowhere upstream** → hard `ref()`, resolved by
   the two-pass refgraph, build-gated against dangling.
5. Nothing to point at → drop the ref and write the rule into `mechanical_notes`
   (§0 rule 4) plus a line in `unmapped_report.json`. Never invent a card.

Three facts about how a softRef lands, all of which matter when deciding:

- `findEntityIdByName` matches on `(categorySlug, name)` and is **case
  sensitive** — the index key is the raw `"$slug $name"`. `"thieves' tools"` does
  not find `"Thieves' Tools"`. The census lowercases (§3.4), so it will tell you
  such a ref resolves when the app drops it.
- It is **qualifier tolerant**: `"Magic Initiate (Cleric)"` falls back to
  `"Magic Initiate"`. This cuts both ways — the built-in pack ships *both*
  `Amphibious` and `Amphibious (Dragon)`, so a softRef to
  `"Amphibious (Aboleth)"` silently lands on the generic row and puts the wrong
  text on the sheet. Qualifier tolerance is a fallback, never a naming strategy:
  emit the name the target actually ships.
- Its index is **first-writer-wins over map iteration order**. With duplicates in
  play, *which* "Fireball" a ref resolves to is an accident of merge order. That is
  the second reason to delete duplicates rather than tolerate them: they make ref
  resolution nondeterministic in a way no test asserts.

The census tracks this surface directly (§3.2 C). It is currently 135 refs —
106 to the built-in pack, 29 that could be in-pack hard refs, 0 dangling, and
**0 to another bundled pack**.

### 2.3.1 A correct ref is not a visible ref — check the reader first

`CharacterResolver` accepts all three envelopes everywhere (`_readRefList` →
`_resolveRef` → `resolveEntityRef`), which is why §2.3 works *on the sheet*. The
chargen UI is not uniformly on that path, and a `_ref` field it filters on is
therefore a **two-sided change**: importer *and* reader.

The live case is `spell.class_refs` (§5.6, phases L3/B7). Four call sites read it
as a list of plain id strings:

| Call site | What it drives |
|---|---|
| `wizard/steps/spells_step.dart` `_classRefs` | the cantrip / prepared-spell picker |
| `wizard/character_creation_wizard_screen.dart` (`spellCount`) | **whether the spells step is required at all** — 0 matches means the step is skipped |
| `wizard/steps/feats_step.dart` | Magic Initiate–style feat spell lists at creation |
| `pending_choice_resolver_dialog.dart` (×2) | the same lists at level-up |

Each does `(fields['class_refs'] as List).contains(classId)`; a `{slug, name}`
Map matches nothing, and `whereType<String>()` drops it outright. Packaged spells
reach these lists today **only** through the parallel `tags` fallback (the class
name as a bare tag, recovered from the v1 fixtures — §4 A0). So:

> Writing `spell.class_refs` as softRefs and retiring the `tags` route in the same
> change **removes every bundled spell from character creation** while every
> number in §3 and §5 improves. This is the shape of regression this audit is most
> likely to ship.

Rule: before filling any `*_ref`/`*_refs` field, grep for its readers. If a reader
is not on `resolveEntityRef`, put it on `resolveEntityRef` **first** (Stage U1),
keep the old route alive until the new one is proven, and only then retire it.

### 2.4 Policy rows that package links have invalidated

These were correct when written and are not any more. Each is re-opened in §5:

| Row | Old rationale | Why it no longer holds |
|---|---|---|
| `spell.class_refs` (required, 0%) | "spell packs ship no class entities, so a `_ref` would dangle" | a softRef to a built-in class does not dangle — it is exactly what 97 subclasses already do |
| `magic-item.base_item_ref` (0%) | "no base items ship in item packs" | the built-in pack ships weapons, armor and gear; softRef by name |

| `monster.gear_refs`, `monster.spell_refs` | ⚪ no counterpart | the *targets* now exist and resolve; whether the source names them is a separate `S` question to re-check |

### 2.5 A name collision is not proof the content is identical — measured

The census matches on `(category slug, lowercased name)`, so every row it reports
is a name collision the resolver can really face. It is **not** evidence that the
two cards say the same thing, and the 2026-07-30 pass measured exactly how weak
the evidence is.

**Measurement (reproduce with the snippet in §7):** of the 1,937 cross-pack shared
names in `creature-action` + `trait`, **1,749 (90.3%) carry different description
text**:

| Category | Shared names | …with differing text | Redundant copies | Distinct variants |
|---|--:|--:|--:|--:|
| `creature-action` | 1,264 | 1,201 (95%) | 1,679 | 1,598 |
| `trait` | 673 | 548 (81%) | 1,105 | 949 |

The examples the previous revision of this section called safe boilerplate are the
worst offenders, because the text names its creature:

| Name | Copies | Distinct texts |
|---|--:|--:|
| `creature-action` "Multiattack" | 8 | **8** |
| `trait` "Pack Tactics" | 7 | **7** |
| `trait` "Amphibious" | 7 | **5** — "The aboleth can breathe air and water" vs "The dragon…" vs "Can breathe air and water." |
| `trait` "Magic Resistance" | 7 | 6 |
| `trait` "Keen Smell" | 6 | 5 |
| `creature-action` "Move" | 6 | 6 |

**And these are not library entities.** A monster hard-`_ref`s its own children:
`action_refs`, `trait_refs`, `reaction_refs`, `legendary_action_refs` are uuid
lists pointing at rows that exist for that one statblock. Collapsing them by name
does not deduplicate a shared card — it reassigns another creature's text to this
creature. The built-in pack already concedes the point by shipping
`Amphibious (Dragon)` next to `Amphibious`.

> **Policy: `creature-action` and `trait` rows owned by a monster are out of scope
> for L1/L2 dedup.** They are per-statblock children, not shareable content. The
> only defensible dedup there is *byte-identical text within one publisher's
> corpus*, and it buys little. **L0 implemented this** — the census identifies
> owned rows from the five `monster` child-ref lists and excludes them from the
> actionable figure, so both categories now read 0.

**What that does to the headline number.** L0 measured it rather than estimating:
3,153 of the 4,331 redundant copies are monster-owned children, leaving **1,178
actionable**. The per-category split is now census output (§3.2) and matches the
estimate below almost exactly — with one correction, gear 47 → **43** (the earlier
figure added section A and B without their overlap):

| Category | Actionable (measured) | Why |
|---|--:|---|
| `adventuring-gear` | 43 | synthesised stubs, no description/cost/weight — drop unconditionally (§6 B6) |
| `monster` | 802 → **per document** | ToB 2016 vs ToB 2023 are deliberate separate editions; A5E restats. Only same-edition reprints drop |
| `spell` | 318 → **~5** | 313 are A5E restats (keep) |
| `background` | 13 | 12 are A5E (keep unless the restat is cosmetic) + 1 cross-pack |
| `feat`, `magic-item` | 2 | inspect individually |

So "20.9% redundant" is the **collision surface**, not the work item. The work
item after policy is 1,178 entities, and §6 L1/L2 exit criteria are written
against that, not against driving section A to 0.

**Sharper than the 90.3% headline, in both directions.** With the census doing the
counting: only **7 of the 1,660** section-A collisions carry the same text as the
built-in card, and **1,749 of the 2,540** cross-pack shared names differ. But 603
of those names have *no prose at all on any copy* — 588 `monster` (the statblock
lives in `attributes`) and 15 gear stubs — so for those, text agreement is not
evidence either way and the decision has to come from `attributes`. `--only monster`
plus a per-document policy is the route, not the text column.

Two documents where dropping the bundled copy would destroy real content:

- **Level Up: Advanced 5e** (`open5e-a5e-*`, `game_system: a5e`) deliberately
  restats 5e material. Its "Fireball" is not the SRD "Fireball", and 313 of
  *Adventurer's Guide*'s 371 spells collide by name with the built-in pack. A5E is
  the case where the answer is most likely **keep**.
- **Tome of Beasts (2016) vs Tome of Beasts 1 (2023 Edition)** are two editions of
  the same book, shipped as two packs on purpose.

`game_system` (`5e-2014` / `a5e`) is display-only metadata — nothing in the app
filters on it, so it cannot carry the decision automatically. The decision is
per-document policy, made once and recorded in §6 L1/L2, not per-row guesswork:

- monster-owned `trait` / `creature-action` rows → **keep** (above);
- synthesised `adventuring-gear` stubs → drop unconditionally (§6 B6 — they carry
  no description, no cost and no weight, and include parse artifacts such as
  "pet monkey wearing a tiny fez");
- statblocks and spells → per document, and A5E most likely keeps its own.

### 3.3 Catalog state

`assets/first_party/manifest.json` carries 19 package entries, **all with
`requires: []`** and **all at `version: 1.0.0`**. Its `counts` and `size_bytes`
also carry pre-existing drift from a pack regeneration that never rebuilt the
manifest — so the manifest is stale independently of anything here, and A0's
rebuild diff must account for it.

The version is not cosmetic. The delivery chain is:

`emit.dart` `pack_version: '1.0.0'` (hardcoded) → `build_catalog` `version` →
`r2_path = package/<slug>@<version>.json.gz` (documented as **immutable**) →
`publish_catalog` `_exists()` → **skip unless `--force`** → client installs
`entry.version` and stamps it as `metadata.catalog_version`.

Consequences this audit has to plan for (§6 Stage D):

- Re-running the whole roadmap and republishing uploads **nothing**: every object
  already exists at `@1.0.0`.
- `--force` overwriting a versioned path contradicts the immutability contract and
  leaves clients with no signal that anything changed.
- There is no installed-pack upgrade path at all: `FirstPartyInstallNotifier`
  installs, it never diffs a stored `catalog_version` against the manifest.
- In debug, `BundledPacksBootstrap` sidesteps all of this with a content hash
  (`metadata.bundled_content_hash`) — which is exactly why the problem is easy to
  miss while developing. Release builds do not ship the assets at all.

### 5.7 The shared grant block

`_FB.grantBlock` puts the same 41 keys — `CharacterResolver.grantFieldKeys`, the
closed contract — on `feat`, `species`, `subspecies`, `magic-item` and `trait`.
`applyGrantsFrom` is the single reader, so one shared helper in the importer
covers all five card types; do not fix this per category.

**`class`, `subclass` and `background` are not on that list, by design.** They use
their own typed fields, and anything level-gated goes on a `features` row pointing
at a Feat card (§0 rule 3). Adding the block to them fails `grant_contract_test`.

Across every bundled pack, exactly **seven** of the 41 keys are ever written:
`granted_skill_proficiencies`, `granted_languages`, `ability_bonuses`,
`granted_damage_resistances`, `granted_senses` (species/subspecies), plus
`granted_armor_proficiencies`, `speed_bonus_ft` and `player_choices` on a handful
of feats. The other 34 are 🔴 everywhere.

Every `*_ref`/`*_refs` key in the block is a §2.3 site: its target is almost always
built-in content.

Highest value first:

1. **`mechanical_notes`** — 0% on all 6,423 traits and all 73 feats. Everything the
   §5 tables describe as "stays in prose" is meant to land here, one rule per
   line, and render under "Other Effects". Nothing else in this list makes a
   previously invisible rule visible.
2. `granted_senses` — needs `range_ft` parsed out of the trait text.
3. `granted_tool_proficiencies`, `granted_feat_refs` — both have a
   `MODIFICATION_TYPES` source tag that the mapper never reads; both 🔗.
4. `resource_pool_grants`, `extra_attack_count_by_level` — these are `{lvl: value}`
   tables, not formulas; they only become fillable after B1/B2 land the level data.

## 6. Roadmap

Ordered by leverage. Each phase has an exit criterion an audit tool can check.

**Every phase inherits three gates:**

1. **§2.3 ref gate** — it may not increase `dupe_census.dart`'s "nothing
   installed" count, and any `_ref` it writes must resolve to existing content.
   *(Trustworthy since L0 2026-07-30: section C resolves the way
   `findEntityIdByName` does. The baseline the gate compares against is **1**, not
   0 — `"Spare The Dying"`, §3.2.)*
2. **§2.3.1 reader gate** — for every `_ref` field it fills, the readers of that
   field are on `resolveEntityRef`, or the phase does not ship.
3. **Repo gate** — `flutter analyze && flutter test` on the touched area, the
   affected `vault/` notes updated, and a `Vault-Changelog` line appended.

**Nothing waits on a snapshot any more** — A0 restored and pinned it on
2026-07-30. L0, U1, T2, T3 and M1 never needed it in the first place.

**The §2.5 text-divergence measurement — superseded by L0.** Kept only as the
independent check on the census's text column; the census's own figures are the
ones §2.5 and §3.2 quote, and they differ slightly by design (this snippet counts
repeats within a single pack as a shared name, and hashes raw text rather than
collapsing whitespace). Run from `flutter_app/`:

```sh
python3 - <<'PY'
import json,glob,collections,hashlib
rows=collections.defaultdict(list)
for f in glob.glob('assets/open5e_packs/*.pkg.json'):
    for v in json.load(open(f))['entities'].values():
        if v.get('type') in ('creature-action','trait'):
            d=((v.get('attributes') or {}).get('description') or '').strip()
            rows[(v['type'],v['name'].strip().lower())].append(hashlib.md5(d.encode()).hexdigest())
multi=[v for v in rows.values() if len(v)>1]
diff=[v for v in multi if len(set(v))>1]
print(f'shared names {len(multi)}, differing text {len(diff)} ({100*len(diff)/len(multi):.1f}%)')
PY
```

`bundled_pack_resolve_test.dart` is the right place to prove a B- or L-phase
landed: it walks an asset the way an install does — resolve every `{_lookup, name}`
against the campaign's Tier-0 rows, then hand the entity to `CharacterResolver` —
so it catches the case where a field is written but nothing reads it, and the case
where a ref points at a card that no longer ships.

**Drift-backed tests on Linux:** `package:sqlite3` opens `libsqlite3.so`, which only
exists with `libsqlite3-dev` installed. `test/support/test_database.dart`
(`openTestDatabase()`) registers a resolver falling back to `libsqlite3.so.0`, so
use it rather than `NativeDatabase.memory()` directly. `v12_schema_smoke_test.dart`
is not on the helper yet and still fails with "Failed to load dynamic library" on
such hosts — that failure is environmental, not a regression.
